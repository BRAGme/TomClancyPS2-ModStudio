# GRAW PS2 — Survival mode, and where the enemy numbers actually live

**Short answer, up front.** GRAW PS2 did **not** inherit Rainbow Six 3's
`AR6DZoneWave` native wave machinery. Nothing in either overlay computes a wave
size, a wave trigger or a difficulty spawn bonus. What the overlay *does* own is
a single mission-script latent command that drives spawning, and it owns exactly
**two numbers**: a **1.0-second interval between spawns** and a **count of 1 per
spawn**. Everything else — how many enemies a round owes, which zone they come
from, when the next wave starts — is **authored per level, inside the level's own
`.DMP` package**, under the GRAW-native property name `m_iNbOfTerroristToSpawn`
and a set of actors named `GR3DZ_Endure_Wave1_A` … `Wave10_B`.

So the R6 3 patch set does **not** port. The GRAW equivalent is a much smaller,
much safer set of code patches (see `patch_candidates.md`) plus a level-data
editor.

All VAs are in `SP.IMG` unless stated. `file offset = VA − 0x000FF800`; see
[loadmap.md](loadmap.md).

---

## 1. `ScriptSpawnTerrorists` — found, decoded, and it is a *script event*, not a native

The string lives at `0x0069CD00`. It is **not** a native `exec` thunk — the
overlay's native thunks all carry a debug name of the form
`intAActorexecSpawn` / `intUParticleEmitterexecSpawnParticle`, and there is no
`intAGR3…execScriptSpawnTerrorists` anywhere in either image (searched, zero
hits). It is an **Unreal `FName`**, constructed at package-registration time by
three autogenerated blocks:

| block | site | FName global it fills |
|---|---|---|
| package A | `0x005433FC` | `0x007A44D0` |
| package B | `0x0054897C` | `0x007A8C60` |
| package C | `0x0054BEA4` | `0x007A6638` |

```
005433f8  addiu  $a0, $sp, 0x494
005433fc  lui    $a1, 0x6a
00543400  addiu  $a1, $a1, -0x3300     ; 0x0069cd00 "ScriptSpawnTerrorists"
00543404  addiu  $a2, $zero, 2         ; FNAME_Intrinsic
00543408  jal    0x17ada0              ; FName::FName
...
00543418  sw     $v0, 0x44d0($at)      ; -> 0x007A44D0
```

Of those three globals, **exactly one is ever read**: `0x007A44D0`, at
`0x0058E50C`. That single read is the whole spawner.

## 2. The spawner: a two-function latent script command

`0x0058E350` is the command's **Init**, `0x0058E430` its **Tick**. They are
consecutive, they share the same object layout, and the Tick is the only reader
of the `ScriptSpawnTerrorists` FName.

### Init — `0x0058E350` (0xDD bytes) — `$a0 = this`, `$a1 = the script node`

```
0058e370  lw    $a1, 8($a1)          ; argument 1 token
0058e374  jal   0x100280             ; EvaluateScriptArg(this, tok, &out)
0058e37c  addiu $v1, $zero, 0x10
0058e380  bne   $v0, $v1, ...        ; type 0x10 = indirect -> deref
0058e390  sw    $v0, 0x34($sp)       ; arg1 value
...
0058e39c  lw    $a1, 8($s0)          ; argument 2 token
0058e3a0  jal   0x100280
0058e3bc  sw    $v0, 0x38($sp)       ; arg2 value
...
0058e3dc  lw    $v0, 0x38($sp)
0058e3e0  sw    $v0, 0x35c($s1)      ; this->remaining  = arg2
0058e3e4  lw    $v0, 0x30($s1)       ; this->Level
0058e3e8  lwc1  $f0, 0x4b4($v0)      ; LevelInfo->TimeSeconds
0058e3ec  swc1  $f0, 0x394($s1)      ; this->lastSpawnTime = now
0058e3f0  lw    $v0, 0x34($sp)
0058e3f8  sw    $v0, 0x358($s1)      ; this->targetIndex  = arg1
```

**So the mission script calls it as `ScriptSpawnTerrorists(targetIndex, count)`.**

### Tick — `0x0058E430` (0x175 bytes) — `$a0 = $s0 = this`

```
0058e440  lw    $v1, 0x358($s0)      ; targetIndex
0058e444  lw    $v0, 0x3e0($s0)      ; this->objectRefCount
0058e448  slt   $v0, $v1, $v0
0058e44c  bnez  $v0, 0x58e45c        ; index out of range -> bail, return 2
...
0058e468  lw    $a0, ($v0)           ; obj = this->objectRefs[targetIndex]  (table at +0x3dc)
0058e474  jal   0x232b00             ; AActor::IsValid()  ==  actor->byte[0x35e] < 4
0058e47c  bnez  $v0, 0x58e4b8

0058e4b8  lw    $v1, 0x30($s0)       ; Level
0058e4bc  lui   $v0, 0x3f80          ; <<<< 1.0f  -- THE SPAWN INTERVAL
0058e4c0  lwc1  $f1, 0x394($s0)      ; lastSpawnTime
0058e4c4  mtc1  $v0, $f0
0058e4c8  lwc1  $f2, 0x4b4($v1)      ; TimeSeconds
0058e4cc  add.s $f0, $f0, $f1        ; lastSpawnTime + 1.0
0058e4d0  c.ole.s $f2, $f0
0058e4d8  bc1t  0x58e554             ; not a second yet -> nothing this frame

0058e4f4  jal   0x58fc10             ; Cast<>(...)
0058e4f8  lw    $a0, 0x480($v0)      ; obj->+0x480 = the script-callable sub-object
0058e500  beqz  $s1, 0x58e53c        ; cast failed -> skip the call
0058e508  addiu $v0, $zero, 1        ; <<<< params.count = 1  -- ENEMIES PER RELEASE
0058e50c  lw    $a1, 0x44d0($at)     ; FName ScriptSpawnTerrorists
0058e514  sw    $v0, 0x38($sp)       ; params block
0058e518  jal   0x17eee0             ; UObject::FindFunction(name)   (582 call sites)
0058e530  lw    $t9, 0x18($t9)       ; vtable +0x18 = ProcessEvent
0058e534  jalr  $t9                  ; obj->ProcessEvent(func, &params)

0058e53c  lw    $v0, 0x35c($s0)
0058e540  addiu $v0, $v0, -1         ; remaining--
0058e544  sw    $v0, 0x35c($s0)
0058e550  swc1  $f0, 0x394($s0)      ; lastSpawnTime = now
0058e554  lw    $v0, 0x35c($s0)
0058e558  bnez  $v0, epilogue        ; still owing -> stay latent
```

The sibling command at `0x0058E220` is built identically but sends
`ScriptIsInLatent` (FName global `0x007A44D8`) with `params = 0` to the same
`obj->+0x480`. Only these two functions ever call the cast helper `0x0058FC10`,
and both fetch `+0x480` in its delay slot — so `+0x480` is a general
"script-callable side object" pointer on the referenced actor, not something
spawn-specific.

### Object layout recovered (the latent-command state)

| offset | meaning |
|---|---|
| `+0x030` | `Level` (the `ALevelInfo`; `+0x4B4` is `TimeSeconds`) |
| `+0x358` | `targetIndex` — script argument 1, index into the object-ref table |
| `+0x35C` | `remaining` — script argument 2, counts down to zero |
| `+0x394` | `lastSpawnTime` (float seconds) |
| `+0x3DC` | object-ref table base (array of `UObject*`) |
| `+0x3E0` | object-ref table count |

Two helpers worth naming, since they show up all over the overlay:

* `0x00232B00` = `AActor::IsValid()`, literally `return actor->byte[0x35E] < 4;`
  (64 call sites). Byte `+0x35E` is the actor's death/state code — the health
  top-up at `0x004701EC` clears it to 0.
* `0x0017EEE0` = `UObject::FindFunction(FName)` (582 call sites).

## 3. Rainbow Six 3's wave machinery: what survived and what did not

### The class names survive in `MP.IMG`, and that proves nothing

`MP.IMG` still carries R6 3's complete deployment-zone class-name pool:

```
AR6DZoneWave             0x005AD9E8    AR6DZonePathNode   0x005ADA70
AR6DZoneRandomPointNode  0x005ADA00    AR6DZonePath       0x005ADA88
AR6DZoneRandomPoints     0x005ADA20    AR6DZoneCircle     0x005ADA98
AR6DZoneRectangle        0x005ADA40    AR6DeploymentZone  0x005ADAB0
AR6DZonePoint            0x005ADA58
```

`SP.IMG` carries only the renamed `AGR3DeploymentZone` (`0x006926F0`).

**Control experiment, and it matters.** In Rainbow Six 3's own SP overlay — where
the wave code demonstrably *does* exist at `0x0040AF28` — the string
`AR6DZoneWave` has **zero** `lui`/`addiu` references and **zero** word
references. Same in GRAW. These strings live in a linker-emitted name pool that
no instruction addresses directly, so **their presence or absence says nothing
about whether the code is there.** Any claim built on "the string is still in
MP.IMG" would be unfounded.

### The code itself is gone — measured, with the caveat stated

Ground truth: `E:\PS2 Games\R6_3_PS2_CutContent\soz_backup\sp.soz.orig`
decompresses to 5,585,280 bytes, SHA-1
`e9bb12138a1e69d551ac9f6b958114e5b2e830da`, matching the value recorded in
`docs/PATCHES.md`. From it I lifted the three documented wave functions and
shape-matched them (masking `j`/`jal` targets, all 16-bit immediates and all
load/store offsets; keeping opcodes and register fields) into both GRAW overlays:

| R6 3 function | R6 3 SP | R6 3 MP | GRAW `SP.IMG` | GRAW `MP.IMG` |
|---|---|---|---|---|
| `AR6DZoneWave::Init` `0x0040AF28` | 1 hit (itself) | 0 | **0** | **0** |
| `AR6DZoneWave::Advance` `0x0040A780` | 1 hit (itself) | 0 | **0** | **0** |
| `AR6DZoneWave::SpawnATerrorist` `0x0040AB60` | 1 hit (itself) | 0 | **0** | **0** |

Tried at 40-instruction and 16-instruction windows, with and without load/store
offsets masked. The `bStasis` bit-extract idiom
(`lbu +0x6f ; dsll32 ; dsra32`) that opens R6 3's `Advance` has **zero**
occurrences in either GRAW overlay, although the compiler idiom itself is alive
and well (`dsll32`+`dsra32` pairs: R6 3 SP 1,999; GRAW SP 2,137; GRAW MP 3,207).

**Honest caveat.** 400 random 16-instruction windows sampled from the R6 3 SP
overlay match into GRAW `SP.IMG` only 15.1% of the time and into `MP.IMG` only
8.0%. The two builds diverged heavily, so a shape miss is *evidence*, not proof.
The proof comes from the data side.

### The data side settles it

A full byte scan of all five vokes archives (3,965,065,960 bytes streamed — see
[data.md](data.md) §6 and `rawhunt.py`) returns **zero hits** in any archive for
every one of `m_iNbToSpawn`, `m_NumberInWave`, `m_bHuntFromStart`, `NbToSpawn`,
`NumberInWave`, `HuntFromStart`, `R6DZoneWave`, `GR3DZoneWave`, `DZoneWave`.
`m_iNbToSpawn` and `m_NumberInWave` are also absent from both overlays.

In a package-serialised engine the property name **must** appear in the level's
name table for the property to be authored. It does not appear. The R6 3 wave
properties are not authored anywhere on this disc.

**Conclusion: GRAW PS2 does not inherit `R6DZoneWave`. The Rainbow Six 3 patch
set (`0x0040AF58`, `0x0040A8A8`, `0x0040AFDC`, `0x0040A874`, and the `bStasis`
gate at `0x0040A790`) has no counterpart here and must not be ported blind.**

## 4. What replaced it: `m_iNbOfTerroristToSpawn` and the "Endure" wave actors

From mining the level packages ([data.md](data.md) §6):

* **`m_iNbOfTerroristToSpawn`** is GRAW's rename of `m_iNbToSpawn`. It occurs
  **exactly once per level package**, in all 33 `.DMP` files (17 in `GR3_1.IMG`,
  15 in `GR3_2.IMG`, 1 in `MENU.IMG`) — i.e. it is a property *name-table* entry,
  with the per-instance values in the package's property blocks.
* **`GR3DeploymentZone`** is the class rename. Hit counts vary per level
  (`S09_A` 10, `SURVIVAL_09A` 9, `S09_B` 8, `ENEMYHUNT_01B` 6, `S03_A` 5, all
  others 2) — that variation is named *instances*, which is what you would
  expect if zones are placed per level.
* **The wave system is called "Endure".** Actors `GR3DZ_Endure_Wave1_A` …
  `GR3DZ_Endure_Wave10_B` — 20 zones, 10 waves × 2 — exist in **exactly one
  file on the disc**: `/GR3_2.IMG → /SURVIVAL_03B.DMP`. Alongside them:
  `SY_DeathCounter_Wave0`, the typo'd `SY_DeathConter_Wave0`, `GR3SquadAI_Wave`,
  and debug strings `++++++ Wave1 Counter` … `Wave10 Counter=`.
* `SURVIVAL_05B`, `SURVIVAL_S11B`, `SURVIVAL_S12A` and four of the five
  `EnemyHunt_*` levels carry **no** level-specific wave actors at all.

None of `m_iNbOfTerroristToSpawn`, `Endure`, `GR3DZ` or `GR3SquadAI_Wave` appears
in `SP.IMG` or `MP.IMG` (searched, zero hits) — the overlay reads these
properties by *offset*, never by name. That is why the numbers are not in the
executable.

### So: what controls a Survival round?

| question | answer | where |
|---|---|---|
| how many enemies a spawn command owes | script argument 2 → `this->+0x35C` | **level `.DMP`**, the mission script |
| how fast they come out | `1.0` seconds, hard-coded | **`SP.IMG` `0x0058E4BC`** (`lui $v0,0x3f80`) |
| how many per release | `1`, hard-coded | **`SP.IMG` `0x0058E508`** (`addiu $v0,$zero,1`) |
| which zone they come from | script argument 1 → `this->+0x358`, an index into the level's object-ref table | **level `.DMP`** |
| the zone's own population | `m_iNbOfTerroristToSpawn` on each `GR3DeploymentZone` | **level `.DMP`** |
| wave structure | the 20 `GR3DZ_Endure_Wave*` actors | **`/GR3_2.IMG → SURVIVAL_03B.DMP`** only |
| per-difficulty enemy count | **nothing — GRAW's difficulty does not touch enemy counts at all**, see §5 | — |

## 5. Difficulty — and the precise negative

GRAW PS2 ships **four** difficulties, set in the menu handler at `0x004AF160`:

| menu button | value written | localised text id |
|---|---|---|
| `B_Recruit` | 1 | `RECRUIT` |
| `B_Ghost` | 2 | `VETERAN` |
| `B_Elite` | 3 | `ELITE` |
| `B_GhostLeader` | 4 | — |

written to the BSS globals `0x007B5F64` (player 1) and `0x007B60F8`
(player 2 / split-screen). `0x004F13A0` then converts 1–4 into a **0-based byte**
stored on the GameInfo object at **`+0x414`** (an actor reaches GameInfo through
`actor->+0x30`).

Searching the whole overlay for every `lb`/`lbu`/`sb` with immediate `0x414`
(excluding `$sp`/`$gp`/`$fp`/`$zero` bases) gives **15 sites: 12 writers and
3 readers**. The three readers are:

1. **`0x00470160`** — `if (difficulty < 2)` then top the player's pawn health
   (`pawn->+0x384`) back up to `0x78` (120) and clear its death byte `+0x35E`,
   and do the same for a teammate against a global floor.
2. **`0x00459570`** — the health-regen tick (`"Player Health = %d"` debug format
   at `0x00693E70`), gated on the same `difficulty < 2`.
3. **`0x003DC338`** — a script-expression evaluator that selects one of four
   authored floats on GameInfo:

```
003dc338  lbu  $v1, 0x414($a0)        ; difficulty 0..3
003dc33c  bne  $v1, 1 -> ...          ; 1 -> GameInfo->+0x4d4
003dc350  bne  $v1, 2 -> ...          ; 2 -> GameInfo->+0x4d8
003dc368  bne  $v1, 3 -> ...          ; 3 -> GameInfo->+0x4dc
003dc37c  lwc1 $f0, 0x4d0($a0)        ; else (0) -> GameInfo->+0x4d0
          add.s $f0, $f0, clamp(x, ±GameInfo->+0x4e0)
```

**Therefore: in GRAW PS2, difficulty controls (a) whether the player and
teammates regenerate health, and (b) one authored float per tier read off
GameInfo. It does not scale enemy counts, wave sizes or spawn rates anywhere in
the SP overlay.** Rainbow Six 3's `m_NbToAddInVeteran` / `m_NbToAddInElite`
difficulty spawn bonuses have no counterpart — there is nothing to patch,
because there is nothing there.

The four floats at GameInfo `+0x4D0..+0x4DC` are authored properties, so they are
edited in data, not code. `R6GAMESETTINGS.INI` ships a matching-looking triple —
`m_fTerroristSkillMultiplier` `{Recruit=0.20, Veteran=0.70, Elite=1.25}` — but
that is **three** values for a **four**-tier menu, so I have *not* established
that this INI key is what feeds `+0x4D0..+0x4DC`. Treat the connection as an
untested guess.

## 6. The level table, and the Survival/Hunt record slots

A flat 32-entry pointer table at **`0x00671720`** names every single-player
level:

```
index  0..21   s01_a s01_b s02_a s02_b s03_a s03_b s04_a s04_b s05_a s05_b
               s06_a s06_b s08_a s08_b s09_a s09_b s10_a s10_b s11_a s11_b
               s12_a s12_b                        (note: s07 is absent)
index 22..26   Survival_03b Survival_05b Survival_09A Survival_S11B Survival_S12A
index 27..31   EnemyHunt_01b EnemyHunt_02a EnemyHunt_04b EnemyHunt_06b EnemyHunt_10a
```

`0x0053A580` is `LevelNameToIndex(const char*) -> int` (returns −1 on miss); it
has 8 callers. Two index patterns fall out of them, and they pin the mode
boundaries exactly:

* `idx − 0x16` (22) → `0x007B5EA8`, five 16-byte records: the **Survival record**.
  At `0x0046F654` the live score `pawn->+0xA90` is compared against
  `record[n]` and stored if higher; at `0x00471828` the record is loaded into
  `pawn->+0xA94` for display.
* `idx − 0x1B` (27) → `0x007B5E50`, five 16-byte records: the **EnemyHunt record**,
  a time (divided by `60.0f` and `3600.0f` for display, labelled `Hud_Timer` /
  `Record` at `0x004C88E4`).

Both tables are in BSS — savegame-backed runtime state, not patchable in the
image.

`SurvivalMode` / `HuntMode` (`0x00696880` / `0x006968A0`) are **menu page names**
in package `PregameMenus`, used only by the main-menu router `0x004B9DF0`. They
are not gameplay flags. The gameplay flags are the `m_b*Game` booleans, and those
come from the per-map INI — §7.

## 7. The live, un-patched data channel: `..\Maps\<MAP>.ini`

`SP.IMG` still contains Raven Shield's per-map INI reader, and it is reached from
seven functions. Format string `"..\\Maps\\%s.ini"` at `0x00699090` (second copy
at `0x0069DEF8`). The queries go through `GConfig` with section
**`Engine.R6MissionDescription`**:

```
0056d558  lui   $at, 0x77
0056d55c  lui   $a1, 0x6a
0056d560  lw    $a0, -0x6c8($at)          ; GConfig
0056d568  addiu $a1, $a1, -0x20f0         ; "Engine.R6MissionDescription"
0056d56c  addiu $a2, $a2, -0x2030         ; "m_bSurvivalGame"
0056d574  lw    $t9, 8($t9)               ; GConfig->GetBool
0056d578  jalr  $t9
0056d57c  addiu $a3, $sp, 0xfc
```

Keys queried in `0x0056D010` alone: `m_bTerroristHuntGame`,
`m_bTerroristHuntCoopGame`, `m_bSurvivalGame`, `m_bTeamSurvivalGame`.
`0x005063A0` uses the same file for `Engine.R6MissionDescription` /
`LocalizationFile` when building the mission list.

The disc's `/MAPS/` directory contains **only Raven Shield map names** — there is
no `MAPS/SURVIVAL_03B.INI`, no `MAPS/S01_A.INI` (see [data.md](data.md) §3).
Each level's `.DMP` bakes in its own INI *filename* (`SURVIVAL_03B.INI`,
`ENEMYHUNT_01B.INI`, `S01_A.INI`), which means the loader is looking for files
that were never shipped.

**Untested guess, flagged as such:** adding `/MAPS/SURVIVAL_03B.INI` with an
`[Engine.R6MissionDescription]` section may be a code-free way to flip mode
booleans. Nothing here demonstrates that the fallback path accepts a file the
retail build never had, and I did not run the game.

## 8. Where the road ends, and the next probe

I can name every number the **overlay** owns and I can show the R6 3 wave code is
not one of them. What static analysis of the executables cannot give you is **the
actual integer values** — how many enemies wave 3 of `Survival_03b` releases —
because those live in the level package's property block, and the `.DMP`
container is not yet decoded.

**The next probe, concretely:** decode `/GR3_2.IMG → /SURVIVAL_03B.DMP`. It is an
Unreal-style package: a name table (the deduplicated ASCII name lists already
visible in a raw dump), then an export table, then serialised property blocks of
the form `nameIndex, infoByte, [size], value`. Find the name-table index of
`m_iNbOfTerroristToSpawn`, then walk the exports whose class is
`GR3DeploymentZone` and read the int that follows that index. The 20
`GR3DZ_Endure_Wave*_x` export names give you a ready-made, unambiguous ground
truth to check the decoder against: they must all resolve to zones, and their
`m_iNbOfTerroristToSpawn` values must sum to something plausible for a ten-wave
Survival round. `SURVIVAL_03B.DMP` is the only file on the disc carrying the full
wave set, so it is both the best target and the only one that can validate the
decoder.
